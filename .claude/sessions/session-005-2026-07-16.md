## The open bug (highest priority next session)
Payfast Sandbox rejects our checkout signature as invalid, even though our own worker's MD5 computation is internally self-consistent (re-deriving the same param string given the same field values reproduces the same hash we sent). This means the *field order or encoding* our `buildCheckoutSignature()` uses doesn't match what Payfast's server actually expects — not a hashing bug.

Root cause suspected, not yet confirmed: `payfast.ts`'s `CHECKOUT_SIGNATURE_FIELD_ORDER` was based on a misreading of the official PHP SDK's `Auth::generateSignature()`. That function does:
```php
$sortAttributes = array_filter($data, function ($key) use ($fields) {
    return in_array($key, $fields);
}, ARRAY_FILTER_USE_KEY);
```
`array_filter(..., ARRAY_FILTER_USE_KEY)` **preserves the input array's own key order** — it does not reorder to match `$fields`. The `$fields` list PHP defines is a *filter* (which keys are allowed into the signature at all), not a *sort order*. If that's right, our `CHECKOUT_SIGNATURE_FIELD_ORDER` constant is wrong: it should sign fields in whatever order they're supplied to `buildCheckoutFields()` (matching whatever order `CheckoutFields` properties get iterated, or more robustly, matching the literal order the fields are listed in the actual outbound Payfast form/query string), not a hardcoded canonical order.

This needs to be verified for certain (ideally by finding a live worked example/test fixture with real field values + expected signature in the SDK's own test suite, the same way `NotificationTest.php` was used to confirm ITN behavior in session 004) before just guessing at a fix — the previous "confirmed against PHP SDK source" claim in `payfast.ts`'s comments turned out to be an incomplete read of `array_filter`'s actual semantics.
