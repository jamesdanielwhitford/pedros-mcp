3. **User journey diagram** — added a Mermaid `sequenceDiagram` (§4) walking a single order end-to-end (menu browse → cart → checkout/elicitation → payment → confirmation), mapping each step to its MCP tool and showing where the customer leaves the Claude conversation to pay.
4. **Removed the "did my order go through?" round-trip** — user asked whether the confirmation step could avoid making the customer ask again. Clarified for the user that MCP has no server-to-client push into an already-closed chat turn (no mechanism for Pedro's server to inject a message into a conversation unprompted), so the fix is architectural, not just wording: the `checkout` tool call stays held open server-side until Payfast's ITN webhook confirms (or a timeout elapses), and Claude reports final status as its next message without the customer needing to ask.
5. **Timeout fallback branch** — added an `alt`/`else` branch to the diagram: happy path (ITN confirms before timeout) reports status immediately; fallback path (timeout elapses first) has Claude tell the customer confirmation is still pending, falling back to the original `get_order_status` polling design when the customer follows up.
6. **Open questions updated to match** — added a 4th open question (what timeout value to use for the held-open `checkout` call, informed by Payfast's real-world ITN latency / Pedro's existing app's observed times) and updated next steps accordingly.

## Decisions / reasoning
- The MCP Connector architecture is additive, not exclusive — a dedicated chat widget remains a possible future client, it's just not the thing being built now.
- Synchronous/held-open `checkout` (rather than a separate polled status check) is the better default UX because MCP has no async push mechanism into finished chat turns — this is a hard protocol constraint, not a design preference, so it was worth stating plainly rather than hedging.
- The timeout-fallback path is necessary, not optional, because ITN latency isn't guaranteed to be sub-turn — silently blocking forever isn't viable, and the original polling design becomes the fallback rather than being discarded.
